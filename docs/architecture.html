기획과 시안을 코드로 함께 만들고, 확정까지 받는 Knot 안의 도구

1정한 것

회의에서 6개를 정했고, 3개는 아직 열려 있다.

확정Knot 저장소 안에 둔다frontend/knotted. 하네스를 쓰려면 Knot 코드와 함께 있어야 한다
확정디자인 정본은 코드Figma가 아니라 실제 컴포넌트가 디자인이다
확정검토 문서 정본은 노션기능 요구사항 검토 DB. 어느 브랜치에서 열어도 같은 문서
확정시안은 제안 브랜치의 코드충돌과 버전 관리는 브랜치가 맡는다
확정범위는 프론트와 디자인백엔드는 지금처럼 노션 검토 문서로

2시스템 구조

세 곳으로 나뉜다. 팀원 컴퓨터에서 만들고, Knot 저장소에 코드가 쌓이고, 바깥 서비스에서 검토한다. 숫자는 일이 흐르는 순서다.

1 채팅으로 기획하고 수정 요청을 보낸다   2 에이전트가 시안을 코드로 쓴다
3 로컬 서버가 저장소 코드로 시안을 띄운다   4 검토 문서를 노션에 쓴다
5 push하면 PR이 생긴다   6 PR마다 미리보기가 배포된다
7 유월이 노션과 미리보기를 보고 결정한다   8 승인되면 develop에 머지

3Knotted가 끼어드는 시점

기능 요청부터 머지까지. 주황 구간이 Knotted에서 일어나는 일이고, 나머지는 지금 하네스 그대로다.

Knotted를 거치지 않는 경우 화면을 보며 정할 일이 아니거나 백엔드 작업이면, 지금처럼 터미널에서 하네스로 노션 검토 문서를 만들고 컨펌받아 구현한다.

4사용자 여정: 시나리오, 화면, 테스트를 하나로

기획, 디자인, 개발이 한 도구에서 일어나면, 셋을 잇는 단위가 필요하다. 그 단위를 사용자 여정(QA 시트의 시나리오 하나)으로 둔다. 화면은 여정의 한 단계이고, 여정은 그대로 E2E 테스트가 된다.

아래 목록에서 시나리오를 고르면 캔버스에서 그 여정의 화면과 화살표만 밝아진다. 화면 카드에는 시안 코드 이름과 요구사항 ID가, 화살표에는 사용자가 하는 행동이 붙는다.

정보가 이어지는 방식

요구사항 ID와 시나리오 ID가 노션과 코드를 잇는 열쇠다. 노션에는 문장을, 코드에는 화면과 행동을 둔다.

여정 파일 하나, 쓰는 곳 셋

시안 화면과 단계를 한 번만 적고 세 곳에서 쓴다. 노션 문장은 옮기지 않고 ID만 적는다.

// logout.journey.ts (제안 브랜치)
export default journey({
  'AUTH-QA-031': [
    { screen: Home.Default },
    { tap: 'MemberProfileAvatar', screen: Home.ProfileMenuOpen },
    { tap: 'ProfileMenu', screen: Home.LoggingOut },
    { screen: Login.Default },
  ],
  'AUTH-QA-033': [
    { screen: Home.Recording },
    // ...
  ],
});

세 가지 쓰임

Knotted여정 화면위 캔버스. 시나리오를 고르면 그 경로만 보인다. 검토도 시나리오 단위로 한다
Knotted흐름 보기 자동 재생단계를 차례로 눌러 실제 앱처럼 움직여 보여 준다
E2E테스트로 변환확정 뒤 단계마다 기대 결과를 더해 Playwright 테스트가 된다. QA 시트 시나리오를 다시 해석하지 않는다

여정이 만들어지고 쓰이는 때

단계시나리오 (노션)여정 파일과 화면 (코드)
기획채팅으로 정한 요구사항에서 시나리오 초안을 뽑아 검토 문서에 둔다시나리오마다 화면을 만들고 여정 파일에 단계를 적는다
검토유월이 시나리오 목록을 보고 빠진 경우를 짚는다시나리오를 고르면 그 여정이 캔버스에서 밝아진다
확정QA 시트 서브 에이전트가 시나리오를 QA 시트 정본에 쓴다그대로
구현읽기만여정 파일에서 E2E를 만들고, 실제 로직을 붙인다
머지 뒤읽기만develop의 여정 파일이 모여 유저 플로우 화면이 된다. 손으로 그리지 않는다

5지금과 비교

회색 줄이 그어진 단계가 Knotted를 쓰면 사라진다. 같은 화면을 두 번 만들고, 같다는 걸 증명하던 일이다.

7무엇을 어디에 두나

새로 만드는 저장소는 없다. 서버와 DB도 만들지 않는다.

Git시안 코드, 도구 코드제안 브랜치와 frontend/knotted. 충돌과 버전은 브랜치가 맡는다
노션검토 문서, 확정 기록기획, 미리보기 링크, 상태, 컨펌한 사람, 날짜
Cloudflare미리보기 화면PR마다 정적 빌드. 노션 내용은 빌드할 때 함께 굽는다
GitHubPR, 승인 기록로직과 테스트 검토는 여기서
저장 안 함수정 요청로컬 Knotted가 연결된 에이전트에게 채팅처럼 바로 보낸다
노션시나리오QA 시트. 사전 조건, 절차, 기대 결과 문장의 정본
Git여정*.journey.ts. 시나리오 ID별로 화면과 행동만 적는다
저장 안 함요소 정보빌드할 때 요소에 붙어 있다

8열린 문제와 제안

회의에서 정하지 못한 세 가지에 대한 제안이다. 팀 확인이 필요하다.

열린 문제 A

시안을 볼 때마다 체크아웃해야 하나

시안은 제안 브랜치에 있다. 검토 문서를 열 때마다 브랜치를 바꾸면 안 된다.

제안 검토는 PR마다 배포되는 미리보기 주소로 하고, 노션 검토 문서에 그 주소를 붙인다. 작업자는 로컬 서버가 브랜치를 worktree로 꺼내 띄워서, 지금 작업 중인 폴더가 바뀌지 않는다.
열린 문제 B

Knotted를 고칠 때마다 PR 승인을 기다린다

저장소 안에 두기로 해서, 도구 코드를 조금 고쳐도 FE 팀원 승인이 필요하다. 회의에서는 라벨로 자동 승인하자는 안이 나왔다.

제안 라벨 대신 바뀐 파일 경로로 판단한다. 라벨은 아무 PR에나 붙일 수 있지만, 경로 기준이면 다른 파일이 하나라도 섞이면 사람 승인으로 돌아간다. 기능 PR의 승인은 병목이 아니라 2차 확인이라 그대로 둔다. 저장소 설정에서 Actions의 PR 승인 허용을 켜야 해서 팀 동의가 필요하다.
열린 문제 C

어떤 형태로 내놓을까

후보좋은 점아쉬운 점
웹 (Cloudflare Pages)Storybook 미리보기와 같은 방식이라 바로 된다. 주소만 열면 된다로컬 작업은 따로 띄운다
데스크톱 앱로컬 작업과 검토를 한 앱에서앱 빌드와 배포를 새로 만든다
스킬knot-feature에서 바로 Knotted를 시작한다화면은 결국 웹이나 앱이 필요하다
제안 웹으로 먼저 시작하고, 스킬은 Knotted를 시작하는 입구로 쓴다. 데스크톱은 도넛 검토(11/19) 뒤에 정한다.

9고민한 것

하루 전에 정한 npm 배포와 md 저장은 회의에서 뒤집혔다. 근거가 틀린 게 아니라 무게가 달랐다.

쟁점회의 전회의 뒤이유
코드 위치개인 저장소, npm 배포Knot 저장소 안하네스와 코드 정본이 승인 병목보다 무거웠다. npm은 누구나 받는다
검토 문서.knotted md 파일노션 검토 DBmd면 문서를 볼 때마다 브랜치를 바꿔야 한다
시안 저장브랜치브랜치 (압축 파일 안 기각)시안을 복원하는 건 버전 관리를 다시 만드는 일
따로 배포별도 앱경로 기준 배포frontend/knotted가 바뀔 때만 미리보기를 배포
범위기획부터 확정까지프론트와 디자인만능 도구로 커질 걱정. 백엔드는 노션으로
검토 단위화면 목록사용자 여정 (새 제안)QA 시트 시나리오, 화면, E2E를 한 줄로 잇는다
상용화처음부터 떼어 내기나중에폴더 하나에 모아 두면 나중에 떼어 낼 수 있다

10폴더 구조

Knotted 코드는 한 폴더에 모은다. 시안 파일만 기능 폴더 옆에 둔다.

frontend/
  src/                          지금 Knot 코드
    modules/features/.../
      ProfileMenu.tsx
      ProfileMenu.draft.tsx     시안 (제안 브랜치에만)
      logout.journey.ts     여정: 시나리오 ID별 단계
  knotted/
    shell/                      Knotted 화면: 제안함, 캔버스, 패널
    runtime/                    iframe 안에서 요소 찾기, 위치 재기
    journey/                    여정 읽기, 여정 캔버스, E2E 변환
    babel/                      요소에 이름과 파일 위치 붙이기
    server/                     노션 읽기와 쓰기, 에이전트, 브랜치와 PR
  webpack.knotted.config.js     기존 설정을 읽어 Knotted 엔트리를 추가
.github/workflows/
  knotted-preview.yml           제안 PR마다 미리보기 배포
  knotted-auto-approve.yml      도구 코드만 바뀐 PR 자동 승인
